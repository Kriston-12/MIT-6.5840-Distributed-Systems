整段戏的高潮在第 8–9 步： B 和 C 都 Get 到「空闲，version=2」，都以为能订。两人同时发 Put(..., version=2)。服务器靠 kv.mu 一次只处理一个：B 先到，写成功，version 变 3；C 的 Put(version=2) 到时版本已经是 3，对不上 → ErrVersion，抢锁失败，只能重新 Get 再来。这就是分布式锁的全部魔法。

两种"锁"别搞混

名字都叫锁，层次完全不同。这是最容易绕晕的点。

kv.mu 保证「往台账上写一次是原子的」（不会两人同时涂改把台账弄成乱码）；分布式 Lock 保证「同一时刻只有一个人在用会议室」。前者是后者的地基——正因为每次带版本检查的 Put 是原子的，你才能用它拼出更高层的互斥。你写 Acquire/Release 时根本不会碰到 kv.mu，你用的是 ck.Put / ck.Get。

还有个坑（unreliable 测试）： 网络会丢包，Put 可能返回 ErrMaybe——"也许成功了也许没有"。所以给每把锁生成一个唯一 ID 当 value，遇到 ErrMaybe 就再 Get 一下：读回来是我的 ID，就说明其实抢到了。Release 同理要能认出"这把锁确实是我持有的"。
